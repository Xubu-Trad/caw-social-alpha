# cawmmunity.caw - decentralized - social

Resilience plan for the alpha frontend and protocol components.

**Status: design proposal, 2026-09-07.** No production provider, domain, storage network, wallet, contract or hosting service is selected. This review used primary documentation and a participating auditor's historical incident account. It ran no network, custody or production failure tests. The existing local prototype is a synthetic demonstration; its current execution evidence is recorded in BOOTSTRAP.md (supporting local record omitted; see the source-coverage note) and the restricted run records.

The target is that losing one named provider or the original team does not erase the public record, prevent another operator from serving the application, or give that provider control over user funds. This must be demonstrated for specific failures. It cannot honestly mean that all networks, devices, storage copies and economic incentives will work forever.

This plan expands the associated website, portable browser application and image/video design. It supplements [ARCHITECTURE.md](ARCHITECTURE.md), [AUTH_AND_KEY_MODEL.md](AUTH_AND_KEY_MODEL.md) and the unresolved source conflicts; it does not replace manifesto requirements with convenient storage defaults. Production permanent-data scope and payment remain OPEN.

## Nine requirements and the dependency/control map

The requirements below are engineering proposals inferred from the cited source behavior. A protocol name alone is not evidence that a deployed system satisfies them.

| ID | Requirement and failure/control boundary | Required recovery path |
|---|---|---|
| RES-01 | **Naming must be replaceable.** DNS depends on registrar, DNS operator and renewal. ENS depends on name ownership, record authority, resolver, chain access and applicable expiry. A name points to content; it does not retain the content. | Publish a release's immutable content identifier and ordinary file hashes separately from the current-name pointer. Preserve a known release and alternate distribution instructions. Record ENS owner/manager/resolver and renewal responsibility, including who can change the pointer. DNS and a single ENS gateway must be optional discovery routes. |
| RES-02 | **Another person must be able to distribute the complete website and app.** GitHub, a web host, CDN, app store, original maintainer and release-signing service are separate dependencies. Multiple URLs under one account do not count as independent operators. | Provide a self-contained static bundle, source, exact build inputs, license/provenance and reproducible packaging instructions. Use relative own-asset paths, ordinary links and a documented HTTP origin. Keep a content-addressed copy and an independently held downloadable archive; no required remote font, script or original account credential. Future release authentication needs an explicit trust/rotation model. |
| RES-03 | **Gateway fallback must preserve integrity and origin boundaries.** The selected gateway can refuse or alter an HTTP response. DNSLink retains DNS dependency. A shared path gateway does not isolate app origins. | Use an isolated origin, such as a per-CID subdomain gateway, or a verified local client. For adversarial gateway integrity, use a client that verifies raw/CAR blocks and paths, or verify a release before executing it. A page cannot establish its own authenticity solely using a verifier supplied by that same untrusted page. |
| RES-04 | **Retain complete bytes under independent control.** A CID, pin request, storage deal or thumbnail is not the original content. Operator failure, unpaid bills, garbage collection, routing and missing blocks are distinct causes of loss. | Candidate baseline: at least three complete copies across at least two independently controlled operators, plus a recoverable offline/export copy. These counts are proposed targets, not a guarantee. Inventory complete content graphs, measure actual retrieval, repair lost redundancy and give another operator the data needed to continue without Xubu. |
| RES-05 | **Image/video posts need an explicit retention contract.** Media originals, thumbnails, transcodes, manifests and public post references have different lifecycles. A frontend's presentation policy must not become account or fund authority. | Preserve the accepted original bytes and their integrity reference; record derived assets separately. Decide which media bytes the manifesto promises to preserve, who pays, replication period, recovery process and what the reader sees when an asset is unavailable. Do not present a locally selected preview as uploaded or permanent. |
| RES-06 | **The public record must rebuild without the original database.** An indexer can omit results or vanish; general RPC access may not include all historical data. Commitments cannot rebuild missing payloads. | Specify chain/contract identifiers, finalized ordering, complete payload availability, versioned serialization and reconstruction rules. Retain independent exports/archives and verify reconstructed balances, ownership, posts, replies and references against canonical evidence. A saved index alone is not sufficient. |
| RES-07 | **RPC and relayers must be replaceable without changing authorization.** An RPC endpoint can censor or report stale state; a relayer can stop sponsoring gas. A common upstream provider can disable several apparent alternatives. | Document direct submission and user-selectable independently operated access. Verify domain, signatures, nonce, expiry, receipts and finality under the eventual protocol. Preserve a direct user exit without the team's signer, while disclosing gas and network requirements. Never label disconnected or pending activity as settled. |
| RES-08 | **Custody must be independent of website administration.** A domain, storage or release key must not authorize transfers. A proxy's implementation can be changed even when its own code is immutable. Immutable code can still contain exploitable bugs or depend on mutable external contracts. | Candidate: a minimal immutable funds core with fully reviewed authority/call graph and original-token semantics. No hidden repair/admin transfer key. Fixes would require separately reviewed deployments and explicit opt-in migration; the old contract is not silently rewritten. Opt-in migration is not a guaranteed escape from a bug that already blocks withdrawals. |
| RES-09 | **Operating and recovery costs must be visible and transferable.** Storage, retrieval, RPC, relaying, domain renewal, maintenance and moderation require resources even when a protocol has no platform fee. | Name each payer and independent replacement, document capacity limits and record measured costs. Separate protocol-required economics from optional frontend service costs. Do not invent a fee, sponsor promise or permanent-storage guarantee to fill a source conflict. |

ENS explicitly describes its Content Hash as a pointer to separately hosted content and identifies the manager's control over that record. The ETH registrar permits renewal by someone other than the owner, which is useful for continuity but does not eliminate other authorities. Sources accessed 2026-09-07: [ENS website records](https://support.ens.domains/en/articles/12275979-add-a-decentralised-website-to-your-ens-name), [ETH registrar, Renewing a Name](https://docs.ens.domains/registry/eth/).

IPFS documents origin isolation per CID for subdomain gateways, warns against hosting apps on shared path gateways, and explains the DNS TXT lookup behind DNSLink. Ordinary reassembled HTTP responses trust the gateway's validation; raw/CAR responses permit client verification. Sources accessed 2026-09-07: [IPFS gateways](https://docs.ipfs.tech/concepts/ipfs-gateway/), [HTTP gateway verification](https://docs.ipfs.tech/reference/http/gateway/).

## Website and app distribution

The associated website should explain the project, link the manifesto and verification material, show what exists today, and open the browser application. The app should retain the requested restrained terminal and imageboard presentation, with participant lanes and readable media posts. Visual resemblance to a live room does not determine canonical protocol storage or make every keystroke a settled action.

For the current local expansion, the intended deliverable is a static website plus the existing browser app, self-contained own assets, a fixed nested `/mirror/` copy demonstration and a deterministic archive assembled from an explicit public-file allowlist. Relative paths should allow the same release to work under a nested HTTP path. The same-machine mirror is a portability check only: it shares a process, device and operator and cannot prove provider independence. Opening JavaScript modules directly through `file://` is not the portability claim.

The archive should contain only the exact release files and a public hash/provenance manifest. Exclude research originals, private run records, credentials, absolute user paths and the workspace. Rebuild the archive twice with fixed ordering/metadata and compare the bytes before claiming deterministic packaging. Archive creation and test results must be recorded by the implementing task; this document does not assert that either check has passed.

A production release would additionally need independent distribution operators and a defined authenticity model. Content identity establishes that a known release is unchanged; it does not establish that an unknown release is trustworthy or newest. A changing DNS/ENS pointer remains a useful convenience with explicit control. Release signing must not give its signers control over protocol balances, and a compromised signing key needs a recovery policy that does not silently make a single maintainer permanent authority.

PWA installation, service workers, offline synchronization and native/mobile packaging are **future proposals**, not implemented capabilities. They require their own update, cache, origin, key-storage and distribution review. No hosting purchase, name registration, pinning account, public tunnel or publication follows from this plan.

## Media and data persistence choices

| Candidate | What it supplies | Residual condition to resolve before adoption |
|---|---|---|
| Independent IPFS pins plus export copies | Content addressing, replication under chosen operators and retrievable content graphs | Every required block needs surviving storage and discoverability. Pay for continued retention and retrieval; test loss of a pinning operator rather than counting gateway URLs. |
| Filecoin storage deals plus a retrieval path | Storage commitments and proof mechanisms for the agreed duration | Renewal, retrieval performance, provider diversity and failure recovery remain necessary. Do not substitute old documentation's deal-duration numbers for current network parameters or live prices. |
| Arweave plus independent exports | A storage endowment and incentive design for durable data | The economics and future preservation assumptions still matter. The yellow paper distinguishes data permanence from network permanence and anticipates future archive succession; it is not proof that a particular app remains online forever. |
| Independently operated ordinary storage plus content hashes and periodic archives | Simple serving, range requests and portable bytes | Accounts, bills and operators can fail. Independence and recovery must be measured; a cloud object URL alone is not the permanent record. |
| Public data on a settlement network, plus retained archival copies | Canonical ordering and integrity under the selected protocol | Execution cost, payload-size limits and historical access must be measured. Do not assume every general RPC retains every old payload. |

IPFS distinguishes caching and garbage collection from pinning. Continued storage requires nodes willing and able to retain and share the bytes. [IPFS persistence, accessed 2026-09-07](https://docs.ipfs.tech/concepts/persistence/).

Filecoin's documentation describes storage proving for a deal's duration and penalties for missing proofs. This review obtained the indexed official text; direct page opening returned an unsupported Markdown content-type error. Its March 2023 numerical limits were not adopted as current parameters. [Filecoin storage proving, accessed 2026-09-07](https://docs.filecoin.io/storage-providers/filecoin-economics/storage-proving).

Arweave's economic and long-term network assumptions appear in sections 3.2.4–3.2.6 of its yellow paper, PDF pages 18–21 in a one-based page viewer. This is a scoped reading of those sections, not validation of their model or current network performance. [Arweave yellow paper, accessed 2026-09-07](https://www.arweave.org/yellow-paper.pdf).

Ethereum's history-expiry roadmap explains why historical data access is a separate design concern. It is not evidence that every discussed change is already deployed across every client. [Ethereum history expiry, page updated 2026-06-30; accessed 2026-09-07](https://ethereum.org/roadmap/statelessness/).

The media record proposal is: original content reference and byte length; validated media type; dimensions or duration where relevant; optional caption/alternative text; and separately identified thumbnails/transcodes. The protocol format, supported codecs, media allowance per post and permanent-versus-optional media scope are unresolved. Public metadata must avoid local filenames, device paths and unnecessary embedded identity information. A production review must decide metadata handling before upload; hashing the original and hashing a redacted derivative are different claims.

Local selection and preview should remain on the user's device and disclose that no upload or network persistence has occurred. Production image/video handling requires resource limits, decoder review, safe rendering and a retention decision. Public distributed storage is not anonymity: IPFS documents public network metadata and unencrypted transport/content considerations. Private messaging remains a separate reviewed encryption and key-lifecycle design, not plaintext media hidden behind an obscure CID. [IPFS privacy and encryption, accessed 2026-09-07](https://docs.ipfs.tech/concepts/privacy-and-encryption/).

## Bounded acceptance tests — proposed, not executed by this review

These are acceptance specifications, not commands or new authorization. Execute only after the relevant implementation and resource plan are reviewed. Local tests use disposable synthetic data, never real funds, real name ownership, public-service attacks or deletion of retained originals. Existing B-001 launch, file, memory, disk and network limits continue to apply; if a proposed fixture exceeds them, revise the bounded plan first.

| Test | Bounded setup and failure injected | Pass evidence and what it does not prove |
|---|---|---|
| OUT-01: static copy | Serve the exact allowlisted release at `/` and the fixed `/mirror/` path in the existing loopback process. Visit website → app → return, load each own asset once, then block the original path in the browser test. One desktop and one narrow viewport; no recursive crawl. | Copied paths still load and the browser makes no external requests. Record file hashes, failed/successful URLs and navigation. This demonstrates local path portability, not independent hosting. |
| OUT-02: release recovery | In a disposable directory reconstruct the static archive twice from the same manifest with fixed metadata. Compare archive and member hashes. Then omit or corrupt one copied asset. No production account or private workspace copy. | Exact matches for good builds; explicit failure for missing/tampered bytes before release acceptance. A test-side hash comparison alone does not implement verification inside the browser. |
| OUT-03: name and gateway loss | Future bounded lab: map two disposable names and gateway fixtures to known content; simulate failed DNS, an unavailable ENS resolution path and an altered pointer without touching real names. Try one alternative route per case. | A saved known release remains reachable; unknown replacements are not treated as that release. Capture resolution source, authority and content verification. Real ENS expiry/renewal operations remain untested. |
| OUT-04: media retention | Future disposable storage lab: inventory at most 20 synthetic media assets within an explicitly approved total-byte cap. Disable one complete copy, not originals. Retrieve every original and referenced derivative from a fresh empty cache through an independent surviving path. | All accepted fixture bytes verify; missing blocks are reported and redundancy can be restored. Test video beginning, middle and end, and full-byte integrity. A poster image loading is not a video-retention pass. |
| OUT-05: index rebuild | Use the approved synthetic fixture size, no more than 1,000 records. Rebuild a new empty index without the original API/database, then compare canonical ordered export, ownership, balances, replies and media references. Include one missing, duplicated and reordered input fixture. | Exact expected outputs or explicit rejection of incomplete/invalid history. Existing two-operator fixture switching is partial evidence only; real archive acquisition and finality remain future work. |
| OUT-06: RPC/relayer loss | Future protocol lab: three bounded cases for unavailable RPC, stale response and unavailable sponsor, plus one duplicated submission. Use local mock endpoints until a separate chain-test plan exists. | User can select a genuine alternate/direct route; unavailable sponsorship discloses gas requirements; no false settlement, replay or duplicated debit. Multiple endpoints with one upstream owner fail the independence criterion. |
| OUT-07: custody and migration | Future contract verification: enumerate every fund-moving entrypoint and authority, then test wrong asset/pair, excess amount, changed beneficiary, expired authorization, replay and unauthorized upgrade/migration in an isolated approved environment. | No path lets a frontend/admin substitute economic fields or move another user's balance. Match reviewed source, compiled bytecode, constructor configuration and linked dependencies. Passing finite tests is not proof of absence of bugs. |
| OUT-08: original team absent | Future recovery drill: an operator with no original credentials receives only the public release, protocol specification and independently available data. Rebuild site, index and retrieval paths; execute only synthetic read/submit/exit fixtures. | Complete log of every needed secret, dependency, manual step, byte count and duration. Any needed Xubu/team-only credential fails the corresponding recovery requirement. This does not simulate total chain or internet failure. |
| OUT-09: budget and degraded state | Use a fixed fixture and bounded request count; stop at the approved time/memory/byte caps. Simulate exhausted media quota, missing content and disconnected history. | Report measured load/rebuild time, peak observed memory, read/write/retrieval bytes and request count. Preserve existing readable data, show unavailable/pending states and do not silently claim permanence or delete originals. No paid load test. |

For future outage experiments, set an explicit request deadline, per-origin concurrency and total transferred-byte cap before running; no unbounded retry or automatic crawl. Record PREPARED, PASS, FAIL or NOT RUN per test with the exact artifact version and observed result. Results cannot transfer automatically to changed files, another provider or another chain.

## Custody and the Team Finance reference

The phrase “Team Finance fiasco” does not identify a particular chain, contract or event in this request. This review does not establish which incident the user means or any current CAW exposure. If the intended reference is the **2022-10-27 migration exploit**, Hacken, a participating auditor, attributes the fault to migration input validation and says its earlier audit scope lacked that later function. Its analysis calls for matching the supplied pair and token amount to the stored lock record. This is an attributed first-party account, not this project's independent reconstruction of the transaction. [Hacken incident analysis, incident dated 2022-10-27; accessed 2026-09-07](https://hacken.io/insights/why-team-finance-was-exploited-for-14-5-million-despite-its-audit/).

The applicable design lesson is to bind every migration and withdrawal to the exact authorized asset, amount and beneficiary, and verify the actual deployed configuration against the reviewed version. Decentralized naming or website mirrors do not repair a liquidity-lock or custody exploit. The site should have no required liquidity-locker dependency merely to stay online.

OpenZeppelin documents how a proxy delegates to replaceable logic under an upgrade mechanism. Therefore “immutable” must describe the full effective authority and external dependency graph, not just one bytecode address. A candidate immutable funds core may reduce discretionary control while making bugs harder to fix; separately reviewed, voluntary migration is a proposal, not a guaranteed rescue mechanism. [OpenZeppelin proxy upgrade pattern, accessed 2026-09-07](https://docs.openzeppelin.com/upgrades-plugins/proxies).

Ethereum documents that third-party nodes may refuse transactions and expose request metadata. Independent node access reduces that provider dependency, while chain operation and transaction inclusion remain external conditions. A documented direct route must exist without implying cost-free or unconditional settlement. [Ethereum run-a-node guidance, page updated 2026-02-24; accessed 2026-09-07](https://ethereum.org/run-a-node).

## Measured budget before a provider decision

No price quotation or spending commitment is made here. Measure: release bytes; accepted media bytes per day; number of complete copies; thumbnail/transcode overhead; retention period; retrieval bytes and requests; index size/rebuild reads; domain/record renewal; relayed actions and gas; maintenance time; and recovery frequency. Report one-time and recurring costs separately, with quote date, units, provider and payer.

Use observed media volume and retention to estimate stored bytes, then apply independent copy count and derivative overhead. Apply actual read demand to egress/retrieval charges separately. Report the cost of rebuilding and restoring one lost copy, not only the steady-state storage price. Run low, expected and high measured-load scenarios before setting allowances or claiming affordability. Present token-denominated costs with their conversion date and assumptions, not a fixed fiat promise.

Every chosen operator needs a recorded replacement/export path and a disclosed funding horizon. If no one pays or preserves the last copy, a content identifier cannot recover erased bytes. If a network stops processing transactions, a mirror cannot manufacture finality. These remaining conditions must stay visible in the product's claims.
